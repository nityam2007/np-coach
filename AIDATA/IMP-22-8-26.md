# Daily Express multi-service booking correction

**Status:** researched and planned on 22 August 2026; **not implemented**. Keep `DAILY_EXPRESS_BOOKINGS_ENABLED=false` until the schema, approved timetable/fare data, atomic inventory, and live acceptance gates in this document are complete.

This document is the authoritative implementation brief for correcting the Daily Express model. It preserves the user-supplied raw notes at the end.

## 1. Required outcome

The public service is not one flat timetable in each direction. It has:

- two route/direction groups for online booking;
- two scheduled buses/services inside each direction, for four bookable daily departures;
- a capacity of 60 on each dated service;
- stop-to-stop fares that may differ by boarding point and destination;
- London <-> Leicester services that remain timetable-only and are sold by the driver, not through online checkout.

Keep the existing SEO route URLs. Separate the route page/direction from the actual scheduled service chosen by a passenger.

```text
London -> Midlands route
├─ Morning service (online, 60 seats)
└─ Evening service (online, 60 seats)

Midlands -> London route
├─ Afternoon service (online, 60 seats)
└─ Evening service (online, 60 seats)

London -> Leicester route
└─ Morning service (Friday-Monday, pay driver)

Leicester -> London route
└─ Afternoon service (Friday-Monday, pay driver)
```

## 3. Verified current-state problems

1. **`routes` currently conflates a direction/SEO page with one scheduled departure.** It can render only one timetable for London->Wolverhampton and one for Wolverhampton->London, so two live services in each direction cannot be represented.
2. **There is no departure choice in the new booking form.** `findJourney()` returns the first published route containing From before To.
3. **Overlapping routes produce the wrong fare.** Production Directus sorts `london-to-leicester` before `london-to-wolverhampton`. Both contain Southall->Slough, so the acceptance booking page currently shows the Leicester fare (£18 single/£30 return) for Southall->Slough. The Daily Express page separately advertises £15/£25, creating a visible contradiction.
4. **Leicester is exposed in the new selectors.** The acceptance booking page includes Leicester even though the live site excludes it from online search and both Leicester pages say "tickets available directly from driver."
5. **The four live scheduled services are missing from Directus.** Production contains only four direction records: one timetable per London-Midlands direction plus the two Leicester directions. All capacities are `0`, so online sales are correctly paused.
6. **Pricing is too coarse.** The new app uses one `price_single` and `price_return` for an entire direction. The WordPress buses use a stop-pair fare grid; the supplied evidence confirms at least £15 and £18 legs.
7. **Return booking is under-modelled.** A return is a second dated service choice in the reverse direction. It must not be represented only as a flat "return price" on the outward route.
8. **Tickets and emails omit essential service data.** The booking row stores departure/return fields, but the boarding pass does not display departure time or return-leg details; the confirmation email and account summary also omit those details.
9. **The current whole-run inventory is safe but conservative.** Every ticket occupies capacity for the whole service even if two non-overlapping stop legs could reuse a seat. Keep this simple behaviour for the first release unless operations explicitly requires segment-level seat reuse.
10. **Some user-facing Daily Express copy is hardcoded in React.** Any touched timetable, travel, fare, availability, or driver-sale copy must move to the existing CMS/fallback path.

There are 48 numeric fare rows in total. Adult, child and infant carry the same amount on every supplied row. Cells showing “Ex: 10” are empty WordPress placeholders, not £10 fares, and remain unavailable online.

Rules for implementation:

- Missing fare row = that stop pair is not sold online on that service.
- Never fall back to another overlapping route or a global flat fare.
- Keep all amounts as integer pence.
- Adult/child/infant may currently have the same price, but persist their quantities separately if operations wants those categories.
- Price a return as the selected outward leg plus the selected return leg unless NP Coaches supplies an explicit return-discount rule.
- Stripe's verified `amount_total` remains authoritative after promotion codes.

## 7. Target Directus model

Use an additive migration; do not delete or repurpose populated production fields in the same release.

### Keep `routes` as the direction/SEO source

`routes` should describe the public direction page, hero, summary, SEO, and general operating notice. Preserve these slugs/URLs:

- `london-to-wolverhampton`
- `wolverhampton-to-london`
- `london-to-leicester`
- `leicester-to-london`

The existing `routes.stops`, `price_single`, `price_return`, and `capacity` fields become legacy compatibility fields after the new model is live. Hide/deprecate them only after verified migration; do not remove them automatically.

### Add `scheduled_services`

One record per actual repeatable bus timetable:

| Field | Purpose |
| --- | --- |
| `code` | immutable unique code such as `lm-morning` |
| `route_slug` | parent direction/SEO route |
| `name` / `label` | CMS-editable customer-facing service name |
| `status`, `sort` | publish/order controls |
| `sales_mode` | `online` or `driver_only` |
| `operating_days` | explicit ISO weekdays, not free-text regex parsing |
| `capacity` | approved sellable seats; 60 for the four online services |
| `stops` | ordered JSON schedule described below |
| `fares` | stop-pair fare rows described below |
| `notice` | optional service-specific customer notice |

Recommended JSON shapes:

```json
{
  "stops": [
    { "code": "southall", "time": "09:45", "boarding": true, "dropping": false },
    { "code": "slough", "time": "10:15", "boarding": true, "dropping": true },
    { "code": "wolverhampton", "time": "14:00", "boarding": false, "dropping": true }
  ],
  "fares": [
    { "from": "southall", "to": "wolverhampton", "adult": 1800, "child": 1800, "infant": 1800 }
  ]
}
```

Validate on the server that stop codes exist, times are valid 24-hour London times, schedule order is unique, `from` precedes `to`, the relevant boarding/dropping flags allow the leg, and fares/capacities are positive integers.

### Upgrade transactional records

`service_runs`:

- add immutable `service_code`;
- use unique `run_key = service_code:YYYY-MM-DD`;
- keep route slug and departure time as readable snapshots/backward-compatible fields;
- copy capacity into the run when first created;
- keep `booked_seats` and `status` private/server-write only.

`bookings`:

- add `outward_service_code` and nullable `return_service_code`;
- persist outward and return departure/arrival times and dates;
- persist adult/child/infant quantities if those categories are approved;
- persist an immutable journey/fare snapshot so later CMS edits cannot change an issued ticket;
- retain existing stop, amount, Stripe, inventory, and idempotency fields.

For the first release, keep the existing conservative whole-service seat counter. If operations later needs seat reuse between non-overlapping stop segments, design a separate row-locked segment inventory change; do not mix it into this correction without approval.

## 8. Required customer flow

1. **Search:** From, To, journey date, optional return date. The online selector contains only the six London-Midlands stops.
2. **Resolve server-side:** find all `online` scheduled services that operate on the date, allow the stop pair in the correct order, have an explicit fare, pass the one-hour London-time cutoff, and are not cancelled.
3. **Choose outward departure:** show every eligible service card with service name, board/drop times and locations, duration, fare per passenger, and live seats remaining.
4. **Choose return departure:** when a return date exists, independently show eligible reverse-direction services for that date. Do not assume the same bus or merely reverse times.
5. **Passengers/contact:** collect approved passenger-type quantities, lead name, email, optional phone, Turnstile, and terms acceptance.
6. **Review:** show both legs, passenger/fare breakdown, subtotal, and total before payment.
7. **Reserve/persist:** atomically reserve the selected dated service run(s), then create the `pending` booking before contacting Stripe.
8. **Stripe Checkout:** use server-computed line items; promotions remain allowed. Never accept a client amount.
9. **Reconcile:** signed webhook idempotently commits paid inventory, records Stripe's final total, releases failed/expired/stale holds, and sends the transactional email once.
10. **Confirmation:** success page, email, account, downloadable boarding pass, and ticket verification must show the selected service, boarding/dropping stop, date/time, passenger breakdown, and both legs for a return.

One booking reference/QR may cover both legs unless operations explicitly asks for one QR per leg.
